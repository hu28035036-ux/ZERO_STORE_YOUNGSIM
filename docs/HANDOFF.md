## 만든 것

Next.js 16 (App Router, Turbopack) + Supabase. 모바일과 데스크톱이 반응형으로
같은 화면을 늘렸다 줄였다 하는 구조가 **아니다**. proxy 가 UA 로 기기를 판별해
서버에서 한쪽 셸만 렌더링한다 (`lib/device.ts`, `components/shell/`).

| 경로 | 하는 일 |
|---|---|
| `/` | 오늘 매출·마진, 재고 자산, 부족 목록, 캐시 불일치 경고 |
| `/stock` | `v_variant_stock` 목록. 검색·필터·정렬(데스크톱은 표) |
| `/stock/new` | 옵션 축 → 데카르트 곱으로 변형 생성 → `create_product` 한 번 |
| `/stock/[productId]/edit` | 상품 기본정보(단위·묶음 이름 포함) + 변형별 판매가·원가·수량·최소재고·입수·바코드 수정 → `update_product` 한 번. 수량 변경은 속으로 실사 전표가 된다. 입수가 있으면 "박스 값을 낱개로 환산" 도우미 |
| `/movements` | `v_movements` 내역. 종류·기간 필터, 페이지 넘김, 정정 |

| `/sales` | 판매 기록 홈. 오늘 요약 + 두 갈래(적기/파일) + 최근 영수증 |
| `/sales/new` | 판매 적기(옛 `/sell` 계산대). 스캔·검색 → 장바구니 → 발생일 → `record_sale` |
| `/sales/import` | 판매기록 파일(엑셀/CSV) 일괄 반영. 업로드 → 열 지정 → 미리보기 → `import_sales` |
| `/sales/batches` | 임포트 이력. 배치·영수증 단위 되돌리기(`void_import_batch`/`void_sale_order`) |
| `/stock/import` | 상품 목록 파일(본사 발주 시트) 일괄 등록. 업로드 → 제목 줄·열 지정 → 이름 정제·중복 감지 미리보기 → `import_products` |
| `/sell` | → `/sales` 리다이렉트 스텁. 한 릴리스만 두고 지운다 |
| `/stats` | 기간 프리셋 + `stats_*` 다섯 개 + 일별 매출 막대 |
| `/settings` | 가게 정보·내 이름·카테고리·거래처·재고 재계산 |

카메라 스캔 버튼은 네 화면에 붙어 있다: `/stock/new`(변형별 바코드 칸),
`/movements/new`(찾기 칸), `/stock`(재고 검색칸 — "이거 몇 개 남았지?" 를 물건을
들고 바로 확인하는 경로), `/sales/new`(판매 적기 스캔칸). `/sales/new` 의
입력칸은 물리 스캐너(키보드 에뮬레이션 + 엔터)도 그대로 받는다 — 카메라는 그
옆의 버튼이고 서로 독립이다.

### 스키마의 뼈대 (이걸 모르면 화면 코드가 안 읽힌다)

1. **`stock_movements` 가 진실이고 `variants.stock_qty` 는 그 캐시다.**
   재고 = `SUM(qty_delta)` 가 정의상 성립한다. `v_stock_integrity` 가 둘의
   불일치를 보여주고 평소엔 0행이어야 한다. 어긋나면 `recalc_stock()`.
2. **원장은 append-only.** UPDATE/DELETE 를 트리거가 막는다. 정정은 지우는 게
   아니라 반대 부호 전표를 하나 더 넣는 것(`void_movement`)이다.
3. **날짜는 예외 없이 KST 로 자른다.** UTC 로 자르면 밤 9시 이후 판매가 전부
   다음 날로 밀린다. 화면에서 날짜를 만들 때도 `+09:00` 을 명시해야 한다
   (`lib/constants.ts` 의 `TIME_ZONE`·`todayInSeoul`, `movements/query.ts` 의
   `kstDayStart`·`kstDayEnd`).
4. **원가는 이동평균이고 입고 전표만 갱신한다.** 판매 전표는 그 시점 원가를
   자기 행에 스냅샷해서, 나중에 매입가가 올라도 과거 마진이 소급해 안 바뀐다.
5. **옵션 없는 상품도 변형 1개를 갖는다.** 재고 경로를 한 갈래로 유지하려는
   것이고, `create_product` 가 변형 0개를 거부하는 이유다.

**카메라 바코드 스캔의 해독기는 기기에 따라 다른 경로를 탄다.** 안드로이드
크롬은 브라우저 내장 `BarcodeDetector` 를 그대로 쓴다. 아이폰 사파리는 그게
없어서(2026-07 웹 검색으로 확인, 애플이 넣을 조짐도 없다) `barcode-detector`
의 ponyfill(ZXing WebAssembly)을 **스캐너를 여는 순간에만** 동적으로
불러온다 — 정적 import 로 두면 안드로이드 기기까지 1.1MB wasm 을 받게 된다.

wasm 파일은 `barcode-detector` 기본값인 CDN(jsDelivr)이 아니라 **우리가
서빙한다.** `scripts/copy-zxing-wasm.mjs` 가 `dev`/`build` 스크립트 맨 앞에서
매번 `node_modules` 의 `zxing_reader.wasm` 을 `public/` 으로 복사하고, 복사본은
`.gitignore` 에 있어 커밋되지 않는다. CDN 을 그대로 뒀다면 CDN 이 막히거나
죽을 때 **아이폰에서만, 그것도 조용히** 스캔이 실패한다 — 안드로이드는 내장
기능을 쓰므로 멀쩡해서 원인을 찾기가 특히 어렵다. 커밋하지 않는 이유는
`zxing-wasm` 버전이 오를 때 `public/` 의 복사본만 옛것으로 남는 어긋남을
막기 위해서다.

읽는 형식은 소매 바코드 다섯 가지(`ean_13`·`ean_8`·`upc_a`·`upc_e`·`code_128`)로
좁혔다 — 다 켜면 프레임마다 해독이 오래 걸리고 오인식도 는다. 카메라는
후면(`facingMode: 'environment'`)에 `width/height ideal 1920×1080` 을 요청한다
— `exact` 로 두면 그 해상도를 못 내는 기기에서 카메라가 아예 안 열려서
`ideal` 이다. 실패 문구는 원인별로 갈린다: https 아님 / 권한 거부 / 카메라
없음 / 다른 앱이 점유(`NotReadableError`) / 화면 재생 실패 / 해독기 로딩
실패 — 원인과 무관하게 문구를 뭉뚱그리면 사람이 엉뚱한 곳에서 헤맨다. 이
저장소가 로그인 실패 문구에서 이미 겪은 사고다(버그 3번, 커밋 `73d896e`).

### 화면을 그릴 때의 규칙

통계 화면을 만들며 정한 것들이다. **되돌리기 쉬운데 되돌리면 나빠지는** 것들이라
적어둔다.

- **한 계열이면 색은 하나다.** 막대 길이에 따라 색을 진하게 하지 마라. 길이가
  이미 크기를 말하는데 색까지 같은 걸 말하면 남은 표현 수단을 낭비하는 것이고,
  범주형 팔레트 검사도 통과하지 못한다.
- **`data-numeric`(= `tabular-nums`)은 세로로 줄이 맞는 곳에만.** 표 안이나 축
  눈금에는 맞고, `StatTile` 처럼 혼자 큰 숫자에는 안 맞는다 — 글자 사이가 벌어져
  성기게 보인다. `components/ui/card.tsx` 의 `StatTile` 에서 일부러 뺐고 주석도
  달아뒀다. 되돌리지 마라.
- **막대마다 숫자를 붙이지 마라.** 최고점 하나만 글로 짚고, 나머지는 "숫자로
  보기" 표로 읽게 한다. 마우스를 올려야만 알 수 있는 값이 있으면 안 된다.
- **판매가 없던 날도 축에 자리를 잡는다.** 있는 날만 이으면 쉰 구간이 붙어서
  추이가 거짓말을 한다 (`stats/period.ts` 의 `eachDay`).
- **색은 뜻이다.** `bg-red-500` 이 아니라 `bg-danger`. 상태는 색만으로 말하지 않고
  항상 글자나 아이콘이 함께 간다 (증감 화살표, 재고 배지).
- **기간·필터는 화면 맨 위 한 줄.** 카드마다 제 기간을 갖게 하면 나란히 놓인 두
  숫자가 서로 다른 기간이라 비교가 안 된다.

## 작업 중 찾아 고친 버그 일곱 개

앞의 셋은 초기 스키마에 있던 것이고, 넷째·다섯째는 브라우저로 띄워보고서야
나왔다. **화면을 붙이지 않았으면 배포 후에야 드러났을 것들**이라, 다음에
스키마를 손댈 때도 같은 태도로 봐라 — "함수가 존재한다"와 "함수가 동작한다"는
다르다. 그리고 "빌드가 통과한다"와 "화면이 뜬다"도 다르다. 여섯째는 성격이
다르다 — 기존 코드가 아니라 이번에 새로 짠 카메라 스캔 코드 자체에 있던
버그이고, 브라우저 스모크가 아니라 코드 리뷰가 잡았다. 일곱째는 처음부터
있었는데 **E2E 를 돌려보고서야** 나왔다 — 눈으로 두 번 누르는 테스트로는
절대 안 잡히는 종류다.

### 1. `void_movement` 이 입고·출고를 정정할 수 없었다 (0012)

부호 제약(`chk_purchase_pos`/`chk_outbound_neg`)이 정정 전표를 고려하지 않았다.
정정은 같은 type 에 부호만 뒤집은 전표라 제약에 그대로 걸린다. **제일 많이 쓰는
두 종류가 막혀 있었고**, 실사는 `adjustment` 로 갈아타서, 판매는 부호 제약이
없어서 우연히 통과하는 바람에 가려져 있었다.

`adjustment` 로 바꿔치기하지 않고 제약을 다시 썼다. `purchase_amount` 가
`qty_delta * unit_cost` 로 생성되는 컬럼이라, type 을 유지해야 정정이 매입
통계를 정확히 상쇄한다.

### 2. `stats_turnover` 는 한 번도 동작한 적이 없었다 (0013)

`full outer join ... on cid is not distinct from cid`. 의도는 맞다(미분류의
NULL 끼리 맞추려는 것). 그런데 PostgreSQL 은 FULL OUTER JOIN 을 merge/hash 로만
실행할 수 있고 `IS NOT DISTINCT FROM` 은 둘 다 아니다. **데이터와 무관하게 항상
`0A000` 으로 죽는다.** 키를 UNION 으로 모으고 LEFT JOIN 두 번으로 바꿨다.

### 3. 로그인 실패 문구가 네트워크 장애를 비밀번호 탓으로 돌렸다 (73d896e)

`signInWithPassword` 오류를 종류와 무관하게 "이메일 또는 비밀번호가 올바르지
않습니다" 로 바꾸고 있었다. 인증 서버에 닿지 못해도 화면은 비밀번호가 틀렸다고
말한다. **실제로 앱을 처음 브라우저로 띄웠을 때 이걸로 한참 헤맸다.**
4xx 만 자격 증명 문제로 보고 나머지는 연결 실패로 말하게 고쳤다.

### 4. 로그인이 통째로 막혀 있었다 — `auth.users` 의 NULL 토큰 컬럼

egress 가 열린 환경에서 처음 로그인해 보고 나왔다. 데모 계정 비밀번호가 맞는데도
`/auth/v1/token` 이 500 을 뱉었다. `get_logs(service: 'auth')` 의 실제 오류:

```
error finding user: sql: Scan error on column index 3, name "confirmation_token":
converting NULL to string is unsupported
```

GoTrue 는 `confirmation_token`·`recovery_token`·`email_change_token_new`·
`email_change` 같은 컬럼을 Go 의 **non-nullable string** 으로 스캔한다. 계정을
Auth API 가 아니라 SQL 로 직접 INSERT 하면 이 컬럼들이 NULL 로 남고, 그러면
**로그인 요청이 데이터와 무관하게 항상 500 으로 죽는다.** 데모 계정이 정확히 그
방법으로 만들어져 있었다 (`.claude/skills/run-app/SKILL.md` 3절이 그 방법을
안내하고 있었는데, 이 함정은 빠져 있었다 — 이번에 추가했다).

NULL 을 빈 문자열로 채워서 고쳤다. **계정을 지우고 다시 만들지 않았다** — 데모
데이터의 `created_by` 가 이 user id 를 참조하기 때문이다. SQL 은 run-app 스킬 3절에
있다. 새 계정을 만들 때마다 그 쿼리를 한 번 돌려라.

여기서 배울 것: 73d896e 가 넣은 "연결할 수 없습니다" 문구는 **egress 차단만
뜻하지 않는다.** 4xx 가 아닌 모든 오류가 저 문구로 나온다. 문구만 보고 네트워크를
의심하다 시간을 버리지 말고 auth 로그를 봐라.

### 5. 판매 화면에서 줄 합계가 잘려 나갔다 (모바일)

계산대 화면이라 제일 중요한데, 장바구니 줄의 오른쪽이 `w-24` 단가 칸 +
`w-24` 합계로 **고정폭 200px** 을 요구했다. 390px 아이폰에서는 그만한 자리가
없어서 다섯 자리 금액(`53,100원`)이 카드 밖으로 19px 밀려 나가 잘렸고, 페이지가
가로로 스크롤됐다.

단가 칸만 좁히는 것으로는 안 된다 — 그러면 이번엔 치는 값이 안 보인다(실제로 한 번
그렇게 고쳤다가 입력칸이 60px 이 되어 네 자리도 잘렸다). 스테퍼는 터치 크기라 못
줄인다. 결국 **자리가 모자라면 단가+합계 묶음을 통째로 아랫줄로 내리게** 했다
(`flex-wrap` + `min-w-56`). 데스크톱은 폭이 남아 안 내려간다 — 1440px 에서 확인했다.

### 6. 상품 등록 카메라 스캔이 옵션 없는 상품에서 값을 조용히 버렸다 (3b3bcb9)

`scanningKey`(지금 스캔 중인 변형 줄)를 `if (scanningKey)` 로 검사했다. 옵션이
없는 상품(이 화면의 기본값)은 `comboKey` 가 `[].join()` 으로 빈 문자열을
돌려주는데, `''` 는 falsy 라 **가장 흔한 경우에서 스캔한 바코드가 조용히
버려지고 있었다.** 오버레이는 정상적으로 열리고 닫혔고 콘솔에도 오류가 없어서,
바코드 칸을 직접 눈으로 확인하지 않으면 알아챌 수 없는 종류였다.

`scanningKey !== null` 로 바꿔 고쳤다. 코드 리뷰가 잡았고, y4m 으로 만든 실제
EAN-13 을 가짜 카메라에 물려 옵션 없는 상품 케이스를 다시 스캔해 회귀가
아님을 확인했다(옵션 2줄 케이스의 각 줄도 함께 재확인했다).

### 7. `ActionForm` 의 2단계 확인이 클릭 한 번에 뚫렸다

`confirmLabel` 을 채우면 "누르기 → 버튼이 빨간 확인 버튼으로 바뀜 → 다시 누르기"
가 의도인데, **첫 클릭이 그대로 제출까지 해버렸다.** armed 전/후 버튼이 JSX
조건부 렌더의 같은 자리라 React 가 **같은 DOM 노드를 재사용**해 `type` 만
`button` → `submit` 으로 바꾸는데, 브라우저는 클릭의 기본 동작(제출)을 클릭
핸들러의 동기 리렌더 **뒤에** 실행한다 — 그 시점 그 노드는 이미 submit 버튼이다.

설정 화면의 재고 재계산·카테고리 삭제 등 **confirmLabel 을 쓰는 모든 곳이 처음부터
이 상태였다.** 사람이 손으로 "두 번 눌러서 되네" 하고 확인하면 첫 클릭에서 이미
실행된 것을 알아챌 수 없다 — E2E 스크립트가 "1단계 클릭 후 armed 확인" 을 하다가
POST 가 이미 나간 것을 잡았다. 임포트 배치 되돌리기가 확인 없이 실행되는 걸로
드러났다.

`key="arm"` / `key="submit"` 으로 두 버튼을 다른 DOM 노드로 강제 분리하고, 보험으로
첫 버튼 onClick 에 `preventDefault()` 를 넣었다. **이 key 를 지우면 버그가
그대로 돌아온다** — 재현 스크립트 없이는 알아챌 수도 없으니 지우지 마라.

### 판매기록 임포트 검증 (2026-07-31, 새로 함)

**마이그레이션 0015 롤백 스모크** — `import_sales` / `void_sale_order` /
`void_import_batch` 를 롤백 트랜잭션 안에서 16항목: 날짜 3개 배치 → 영수증
3장·KST 일자 정확, 같은 지문 재호출 `23505` 거부, `p_force` 통과, **직접
쓰기(`record_sale`)는 같은 내용 반복도 안 막힘**(부분 유니크의 존재 이유),
단가 생략 시 `sale_price` 폴백, 재고 = `SUM(qty_delta)`·무결성 0행, 영수증
합계 = 원장 되읽기, 배치 되돌림 후 재고 원상·**일별 매출 0**·오늘 버킷 유출
없음, 이중 되돌림 거부, 되돌린 영수증 `item_count` 0.

이 스모크가 설계 결함 하나를 잡았다: 처음엔 `void_sale_order` 가
`void_movement` 를 그대로 썼는데, 그러면 반대 전표가 "정정한 오늘"에 앉아
**지난 날짜 매출은 부풀려 남고 오늘에 음수가 쌓인다**(총계만 맞다). 임포트
취소는 반품이 아니라 "잘못 넣은 기록의 취소"라 반대 전표를 **원본 날짜**에
직접 넣는 것으로 바꿨다. 입출고 정정(`void_movement`)은 안 바꿨다 — 거기는
정정 시점이 남는 게 맞다.

**E2E — 실제로 확정 버튼을 눌렀다** (검증용 상품 2개를 만들었다가 검증 후
전부 지웠다, 사용자 승인 받음): 업로드 → 열 자동 추측 5/5 → 매칭(바코드
정확·이름 정확 둘 다) → 미리보기(재고 변화 표) → **확정 → 영수증·합계 정확**
→ 같은 파일 재업로드 → **매핑 기억으로 열 지정 건너뜀 + 중복 감지 카드** →
이력에서 배치 되돌리기(2단계 확인) → 재고·일별 매출·무결성 전부 원상.
파싱 순수 함수는 node 로 24케이스(CP949 CSV·BOM·따옴표 안 쉼표·탭 구분·
`1,600원`·엑셀 Date 의 KST 일자 등) 전부 통과.

**재편 후 화면 스모크** — 프로덕션 빌드를 Playwright 로 두 셸 × (`/sales`
`/sales/new` `/sales/import` `/sales/batches` `/stock`) + `/sell`→`/sales`
리다이렉트: 전부 `main` 에 내용, `h1` 1개, 콘솔 오류 0, 가로 스크롤 없음,
`/stock` 스캔 버튼 존재. **검증 데이터 정리 후 빈 상태에서 한 번 더 전부
통과.** 스크린샷을 눈으로 봤다 — nav 순서(재고가 판매 앞), 모바일 탭 라벨

### 초도 데이터 박스 기준 정리 (2026-08-01, 실데이터를 실제로 고쳤다)

**초도 임포트가 시트의 `입수` 열을 박스당 개수로 잘못 읽었다. 그 열은 발주
수량이다.** 시트 360행 중 349행에서 `합계금액 = 매입가 × 입수` 가 성립한다 —
이게 결정적 증거다. 그 값이 `units_per_pack` 과 `stock_qty` 양쪽에 들어가는
바람에 박스 하나를 1개로 세고 박스 가격을 낱개 가격으로 쓰고 있었다.
**진짜 박스당 개수는 제품명(→ `products.description`) 안에 있다.**

추출 패턴은 이 순서다 (구체적인 것 먼저): `N개입` → `N입` → `/NEA` → `N개` →
`N팩` → (추정) `g×N` 총중량 검산 → (추정) 총중량÷낱개중량. 뒤의 둘은 `입` 앞
숫자가 빠진 오타(`200g*5 1Kg/EA`, `260g*입 1.3Kg/EA`)를 위한 것이고 검수표에
"추정"으로 표시했다. **`N개`·`N팩` 패턴이 처음엔 빠져 있었는데**, 그 탓에
`단슐랭 카사바칩`(규격 "50개", 수량 1, 판매가 85,000원) 같은 명백한 박스가
낱개 상품으로 새어나갔다 — 검수표를 눈으로 훑다 잡았다. 규격 표기가 제각각이라
패턴만으로는 끝내 다 못 잡는다는 뜻이기도 하다.

사용자 결정 넷: ① 묶음(`30g*5입 150g/EA` 등)도 낱개로 판다 → `/EA`·`/BOX`
가리지 않고 N≥2 면 환산 ② 수량과 가격을 함께 환산(수량 ×N, 가격 ÷N)
③ 검수표 승인 후 반영 ④ **박스당 개수는 모든 품목에 적는다.**

**환산과 기록은 다른 일이다. 섞으면 맞는 값이 망가진다.**

`CJ 비비고 닭가슴살 김치만두`는 사용자가 확인하며 실사 12 + 입고 1 을 넣어

× 12 = 12개**로 되돌려 환산했다("엑셀표에 나와있는대로" — 사용자 지시).

**반영 방식 — `update_product` RPC 를 쓰지 않았다.** 그 함수는 화면이 "언제나
현재 상태 전체를 보낸다"는 전제라 대량 작업에 함정이 둘이다: `description`·

근거다), 변형 항목에 `barcode` 를 빼면 **기존 바코드를 DELETE 한다**(351개).
대신 로그인 계정으로 supabase-js 를 통해 상품마다 두 문장을 돌렸다:

1. `variants` 의 `sale_price`·`cost_price`·`units_per_pack` UPDATE
2. `record_stocktake(variant_id, 새수량, '초도 박스 기준 정리')`

**①이 ②보다 반드시 먼저다.** 실사가 먼저 들어가면 원장 트리거가 낡은 박스
원가를 전표에 스냅샷한다(0003 의 `new.unit_cost := v_cost`). 검증 쿼리로
`note = '초도 박스 기준 정리'` 인 전표 302건의 `unit_cost` 가 전부 새 원가와
같은 것을 확인했다 — 이 순서가 지켜졌다는 직접 증거다.

한 트랜잭션으로 묶지 않았다. supabase-js 로는 안 되고, 대신 **멱등**하게 짰다 —
목표 상태가 검수표에 고정돼 있어서 이미 맞으면 건너뛴다. 중간에 끊기면 다시
돌리면 된다. `created_by` 가 `auth.uid()` 기본값이라 MCP(service role)가 아니라
로그인 계정으로 돌려야 전표에 사람이 남는다(초도 반영 때와 같은 이유).

검증: 무결성 0행 · **재고자산 11,118,466원** — 초도 등록 당시 기록(11,118,464원)과
2원 차이로 되돌아왔다. 이게 가장 강한 근거다 · 총재고 1,169 → 5,713점 ·
`units_per_pack = 1` 인 행 0 · 정리 전표 302건 전부 `stocktake`·작성자 있음 ·
**변형마다 마지막 정리 전표의 `unit_cost`·`counted_qty`·`stock_after` 가 현재
값과 전부 일치(302/302)** — 가격을 수량보다 먼저 고쳤다는 직접 증거다 ·
append-only 트리거 `O` · 표본 6종(딸기잼·햇반·초코볼·김치만두·피자칩·코카콜라)
시트와 일치, 그중 피자칩(B)·코카콜라(C)는 **수량·가격이 안 바뀐 것까지** 확인 ·
배포 앱 두 셸 × `/`·`/stock`·`/stats`·`/movements` 콘솔 오류 0·가로 스크롤 0.

"전표 원가 = 현재 원가" 는 **변형마다 마지막 전표로만** 따져야 한다. 원장이
append-only 라 아래의 2차 수정을 거친 6건은 옛 전표에 옛 원가가 그대로 남아
있고, 그건 오류가 아니라 이력이다. 전체 전표로 세면 6건이 어긋난 것처럼 보인다.

#### 사후 감사에서 잡은 버그 — 비고란의 행사 문구를 박스당 개수로 읽었다

반영을 마친 뒤 **검수표를 근거로 쓰지 않고 원본 엑셀과 DB 만 놓고 다시** 따졌다
(`audit.mjs` 방식). 거기서 실제 오류가 나왔다.

임포트는 시트의 **비고란을 `description` 뒤에 ` · ` 로 이어붙인다.** 그래서
`한끼통살 …주먹밥` 의 규격이 `데리야끼맛 100g/EA · 상시행사품목(2개 구매시
1,000원 할인)` 이 되고, `N개` 패턴이 그 **"2개"** 를 물었다. 낱개 주먹밥 6종이
N=2 로 환산돼 수량 10→20, 판매가 2,100→1,050원이 됐다. 고친 규칙은
**` · ` 앞부분(규격)만 본다**. 그러면 `100g/EA` 만 남아 아무것도 안 뽑히고,
그게 맞는 결과다(낱개 상품 → 박스당 개수 빈칸).

같이 잡힌 것: `제로스토어 전용비닐봉투` 는 소모품이라 환산에서 뺐는데 **B 갈래
비우기에도 안 들어가서 `units_per_pack` 에 발주수량 10 이 남아 있었다.**
제외 처리가 "아무것도 안 함"이라 어느 쪽에도 안 걸린 것이다. 빈칸으로 고쳤다.

교훈: **재고자산 검산은 N 이 틀려도 통과한다.** 수량 ×N 과 원가 ÷N 이 상쇄되기
때문이다. N 자체를 검증하는 독립 근거는 규격의 무게 계산(낱개중량 × N = 총중량)뿐이고,
그걸로 확인된 것은 242건이다. 나머지는 눈으로 봐야 한다 — 실제로 그렇게 잡았다.

**규칙으로 못 정한 2건 — 사용자가 "갯수 적혀있는대로" 로 결정했다:**

- `옐로욜로 카카오칩` — 규격 `25g*35입 600g/BOX` 가 자기모순이다. 25g×35 = 875g
  인데 총중량은 600g 이라 무게로는 24 다. **표기를 따라 N=35**(2,700원). 정규식이
  뽑는 값과 같아서 코드에 따로 넣을 것은 없다.
- `고맙당 저당 불닭소스(10개)+저당 핫불닭소스` — 이름이 "불닭소스(10개)+핫불닭소스
  (10개)" 라 병이 20개다. 임포트가 **뒤쪽 괄호만** description 으로 떼어내는 바람에
  규격에 "10개" 만 남았고, 그대로 읽으면 N=10 — 한 박스가 10개로 쪼개진다는 뜻이라
  내용물 20병과 어긋난다. **N=20**(수량 20 · 원가 6,000 · 판매 8,700원)으로 고쳤다.
  이 값은 데이터에서 못 뽑으므로 스크립트에 `사람이정한N` 으로 박아뒀다 — 규칙이
  아니라 사람의 판단이라는 것을 드러내려고 일부러 따로 뒀다.

최종 상태: **350건이 시트와 일치, 어긋나는 줄 0건.** 무결성 0행 · 재고자산
11,118,466원 · 총재고 5,723점 · `units_per_pack = 1` 인 행 0 · 빈칸 50 ·
마지막 정리 전표 어긋남 0 · append-only 트리거 `O`.

**되돌리려면** `docs/0018-박스기준정리-이전값.json` 의 `현재*` 열이 유일한 이전
값 원본이다. 원장이 append-only 라 전표를 지우는 게 아니라 반대 실사를 하나 더
넣는다. `void_product_import('6d725244-…')` 는 **이제 영영 못 쓴다** — 초도 전표
뒤에 다른 전표가 있으면 거부한다.

```sql
  delete from public.products;
  delete from public.suppliers;
  -- 카테고리 4개와 app_settings 1행은 원래 시드다. 지우지 마라.

  alter table public.stock_movements enable trigger trg_movements_append_only;
commit;

-- 확인: 아래가 전부 0 이어야 하고, 트리거는 다시 살아 있어야 한다
select (select count(*) from public.stock_movements) movements,
       (select count(*) from public.products) products,
       (select tgenabled from pg_trigger
         where tgname = 'trg_movements_append_only') as trigger_enabled; -- 'O' 여야 정상
```

**계정은 지우지 마라 — 이건 지금 사람이 실제로 로그인해 쓰는 계정이다.** 지우면
앱에 들어갈 수단이 없어진다. 데모 데이터 정리는 위 SQL(상품·변형·전표·거래처)
까지만 하고 `auth.users` 행은 남겨두는 것이 기본이다.

정말 계정까지 지워야 하는 상황(예: 계정 체계를 통째로 새로 만드는 경우)이면
**먼저 로그인할 다른 계정을 확보한 뒤** 아래로 지운다 —
`delete from auth.users where email='cwyh5088@zerostore.kr';` 또는 user id

지워지고, 전표 45건의 `created_by` 참조는 끊긴 채로 남는다).

### 마이그레이션 버전 불일치 — 2026-07-31 에 맞췄다

원격 `supabase_migrations.schema_migrations` 의 version 이
`20260730114743`~`20260730150059` 였다. MCP `apply_migration` 이 자체
타임스탬프를 찍어서 로컬 파일명(`20260730000001`~`20260730000013`)과 어긋나 있었고,
그대로 두면 `supabase db push` 가 13개를 전부 미적용으로 보고 재실행하려 한다.
사용자 확인을 받아 **원격 version 을 파일명에 맞췄다.**

파일명 쪽을 원격에 맞추는 방법도 있었지만 그러지 않았다. 이 문서와 커밋 메시지가
마이그레이션을 `0012`·`0013` 처럼 부르고 있어서, 파일명을 바꾸면 그 참조가 전부
깨진다. 바꾼 것은 이력 테이블의 version 문자열 하나뿐이고 앱 데이터·스키마와는
무관하다 (바꾼 뒤 상품 5·변형 9·전표 45·영수증 24, `v_stock_integrity` 0행,
append-only 트리거 살아 있는 것을 확인했다).

**적용된 SQL 이 파일과 같은지도 확인했다.** 원격 `statements` 에는 설명 주석이
빠져 있어 길이가 더 짧게 보이는데(예: 0001 은 451자 대 693자), 실행되는 문장은
같다. DB 에 빠진 것은 없다.

되돌려야 하면 아래로 원래 값으로 돌아간다. 이름 13개가 전부 유일해서 매핑 키로
안전하다:

```sql
update supabase_migrations.schema_migrations m
   set version = v.old_version
  from (values
    ('extensions','20260730114743'), ('core_tables','20260730115428'),
    ('ledger','20260730120010'),     ('rpc','20260730120401'),
    ('views','20260730120904'),      ('stats_functions','20260730121105'),
    ('rls','20260730121136'),        ('auth_hooks','20260730121156'),
    ('grants','20260730122109'),     ('product_rpc','20260730135024'),
    ('movement_view','20260730142420'),
    ('fix_void_sign_constraints','20260730143216'),
    ('fix_stats_turnover','20260730150059')
  ) as v(name, old_version)
 where m.name = v.name;
```

**앞으로 MCP `apply_migration` 을 쓰면 또 어긋난다.** 새 마이그레이션을 넣은 뒤에는
version 이 파일명과 같은지 확인해라.

## 작업 방식 메모

### 스모크 테스트는 롤백 트랜잭션으로

프로덕션 DB 에 직접 붙어 있으므로 흔적을 남기지 않는다. 결과를 `raise exception`
메시지에 담아 던지면 전부 롤백되면서 결과는 볼 수 있다 (NOTICE 는 MCP 로
안 돌아온다).

```sql
do $$
declare r text := '';
begin
  -- ... 실제로 RPC 를 부르고 결과를 r 에 누적 ...
  r := r || format(E'\n1) 재고=%s (기대 30)', v_after);
  raise exception 'SMOKE%', r;   -- 전부 롤백되고 메시지는 에러로 돌아온다
end $$;
```

끝나고 `select count(*)` 로 정말 비었는지 확인할 것. 카테고리 4개와
`app_settings` 1행은 원래 시드 데이터라 남아 있는 게 정상이다.

### PostgREST `or()` 에 사용자 입력을 그대로 넣지 마라

`or()` 는 쉼표로 조건을 나누고 괄호로 묶는 문법이라 상품명에 친 쉼표 하나에
필터가 통째로 깨져 400 이 난다. `lib/search.ts` 의 `likePattern()` 을 써라.

### 정렬 키를 URL 에서 그대로 받지 마라

없는 컬럼이면 400 이 난다. 화이트리스트로 받는다 (`stock/query.ts` 의 `SORTS`).

### 서버 액션은 UI 없이도 POST 로 불린다

proxy 의 검사는 최적화이지 방어선이 아니다. 모든 액션 첫 줄에서 `requireUser()`.
